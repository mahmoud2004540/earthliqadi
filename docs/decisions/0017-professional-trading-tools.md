# ADR-0017: Professional trading tools — agent API keys, batch orders, cancel-all, dead-man switch

- Status: Accepted (part 1 of product step B)
- Date: 2026-11-06
- Context: product brief rev 2 — professional and algorithmic traders need
  programmatic access that is safe for a self-custody venue.

## Decision

### 1. Agent API keys

The key pair is **Ed25519**, generated by the trader's bot. Only the public
key is registered; the private key never reaches us, so there is no shared
secret to leak from our database.

**Authorisation is two steps and needs the account's wallet** (wallet
accounts only):

1. `POST /v1/me/api-keys/challenge {label, publicKey, scopes, allowedIps, expiresInDays}`.
   The server builds the text to sign, which states the key, its scopes,
   IP allow-list and expiry. The text is single use and valid for 5 minutes.
2. `POST /v1/me/api-keys {challengeId, signature}` with `personal_sign` over
   that exact text. The recovered signer must be the account's wallet. The
   message and signature are stored as evidence.

**Scopes** are `read` and `trade`, enforced by a database CHECK. **No scope
can withdraw or manage keys.** At most 10 active keys per account, each with
an expiry of up to 365 days and an optional IP/CIDR allow-list. What was
authorised is immutable (trigger); only `last_used_at` and a one-way
`revoked_at` can change.

**Request signing.** Each request carries:

- `X-API-Key: <key id>`
- `X-API-Timestamp: <ms>` (±30 s)
- `X-API-Signature: base64(Ed25519(timestamp \n METHOD \n path?query \n raw body))`

The signature is verified over the **exact received bytes** (raw body). Each
signature is single use within the skew window (Redis `SET NX`).

**Allow-list of routes.** API-key requests are accepted only on handlers
marked `@ApiKeyScope('read' | 'trade')`. All other routes answer
`403 API_KEY_NOT_ALLOWED`, including vault withdrawals, key management and
sessions.

| Scope   | Routes                                                                   |
| ------- | ------------------------------------------------------------------------ |
| `read`  | orders list/get, my trades, balances, ledger history, positions          |
| `trade` | place, batch, cancel, reduce, cancel-all, cancel-after, leverage, margin |

The effective permissions are the key's scopes intersected with the owner's
customer permissions. Staff permissions are never reachable with a key.

**CSRF.** Requests that carry `X-API-Key` skip the CSRF check. They use no
cookies, and browsers cannot add these headers cross-site without a CORS
preflight, which the API never allows.

### 2. Batch orders

`POST /v1/orders/batch` accepts up to 20 orders. Each order is its own
transaction, so no partial hold is ever left behind. The response lists
per-item results (`202`, `200` when replayed, or the error). The batch counts
as one request for the per-user rate limit.

### 3. Cancel-all

`POST /v1/orders/cancel-all {market?}` enqueues a cancel for every open order
and returns how many were requested.

### 4. Dead-man switch

`POST /v1/orders/cancel-after {timeoutSeconds}` (5 s to 1 day; 0 disables)
stores a deadline. Clients refresh it while they are healthy. A scheduler
(`CANCEL_TIMER_POLL_MS`) claims expired timers with `FOR UPDATE SKIP LOCKED`,
cancels all of that user's orders and audits the event. It is safe with
several API instances.

## Not in this part

These follow in part 2 of step B:

- order-book diffs with sequence numbers over WebSocket;
- take-profit / stop-loss on positions;
- sub-accounts;
- API-key authentication for the private WebSocket.
